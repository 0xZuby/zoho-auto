MVP feature plan ( InsideOps ) 
The idea
Turn each authorized HR request into a traceable lifecycle run. Routine, well-defined cases flow automatically through Google and Zoho; anything ambiguous or unsuccessful stops in an exception queue for an admin. This removes repeat admin work without hiding failures or making uncertain decisions automatically.
MVP outcome: For an authorized, complete request, create the right account(s), send setup invitations, and enforce the required security policy—or block access on an employee’s effective leave date—with every step recorded.
Signature interaction: the lifecycle run
A request is represented by one status timeline, from intake through each system action. The admin sees what is complete, what failed, and the next safe action. A retry resumes only the failed step; it does not create duplicate accounts or repeat successful work.
This makes the key interaction useful in a short demo: submit one request, watch each step complete, and see an actionable exception if an integration fails.
Scope recommendation
Ship Phase 1 as four connected capabilities:
Structured intake and centrally managed rules — no more formula-driven email or account-type decisions.
Automated onboarding — Google account or identity, Zoho mailbox where applicable, setup invite, and 2SV policy.
Scheduled access blocking for leavers — disable relevant accounts and access on the effective date.
Operations and evidence — exception queue, notifications, retry/cancel controls, and audit log.
Keep default InsideMaps role assignment out of the launch-critical path unless its mapping and API are ready and approved. Keep additional-role requests, data handover, delayed deletion, approvals, and full employee status views for later phases as indicated in the PRD.

MVP acceptance criteria
1. Request intake
As an authorized HR submitter, I can submit a new-hire or leaver request in one place so it enters a trackable workflow.
Required fields are validated; malformed or incomplete requests do not run; accepted requests appear in the queue within 5 minutes. Each request has a unique ID.


As a submitter, I can see whether my request was received or needs correction.
The submitter receives a clear validation or receipt message; personal data is only visible to permitted roles.
2. Provisioning rules
As an admin, I can manage approved positions and their account-type mappings without changing code.
Every active position maps to exactly one account type; unknown or unmapped positions are blocked and routed to exceptions.


As an admin, I can configure the company email domain rule.
Email generation follows the approved normalization and naming rules; Ops/domain mapping is explicit and testable.


As an admin, I can see the proposed address before or during provisioning.
Collisions are checked against existing Google and Zoho accounts; the next available suffix beginning with 2 is used; adjusted addresses are recorded and surfaced.
3. Onboarding execution
As an admin, I can have the system create a full Google account or Google identity according to the position mapping.
The correct account type is created in the configured org unit and groups; identity-only users do not receive Gmail.


As an admin, I can have Zoho mailboxes created for users whose account type requires them.
The mailbox uses the derived address; retries are idempotent; partial Google/Zoho failures are visible rather than silently treated as success.


As a new hire, I receive setup instructions at my private email.
The invite goes to the submitted private email; first-login password change and the required 2SV policy are applied; admins can see 2SV enrollment status where available.


As an admin, I can process one request or a batch without building CSVs.
One and 20+ concurrent requests use the same flow; each request has its own status and error handling.
4. Offboarding
As an authorized submitter, I can record an employee’s effective leave date.
The date and employee identity are validated; the request is scheduled against the agreed timezone and effective-time rule.


As an admin, I can trust the system to block access on the effective date.
Within 15 minutes of the effective time, the system suspends the Google user, revokes sessions/tokens, disables Zoho where applicable, and removes InsideMaps roles where the integration is supported. Every result is recorded.
5. Exceptions and recovery
As an admin, I can see requests that are blocked or failed and why.
The exception queue shows the failing step, system, reason, and partial completion state.


As an admin, I can correct eligible inputs, retry a failed step, or cancel the request.
Retrying does not duplicate completed work; the retry or cancellation is audited. Risky or ambiguous cases never proceed silently.
6. Notifications and audit
As a requester or admin, I receive completion or failure notifications.
Notifications include request ID, affected accounts, outcome, and next action. Notify managers only when a manager contact is already available or is added to the approved Phase 1 intake.


As an auditor, I can reconstruct what happened to a request.
Each action records request ID, actor (person or service), system, action, result, and timestamp; access to private emails and names is restricted.

Screens for the Phase 1 product
The existing nine-screen plan maps well to the MVP. The dashboard, intake, request detail, exceptions, rules, and audit log are core. Offboarding intake is core if the existing request source provides the effective date. Keep offboarding status and provisioning review focused on operational progress not a separate approval workflow. A fuller employee status view belongs to Phase 2.

Explicitly out of scope for launch
Approval workflows, unless the business decides they are required before execution.
Start-date scheduling for onboarding and manager as a new required intake field.
Data transfer, retention-period handling, delayed deletion, and license recovery.
Extra InsideMaps role requests and non-default role management.
Slack and GitHub automation; those needs remain visible for manual follow-up.
Device management, client accounts, and client users.
Launch gates and unresolved decisions
Resolve these before enabling live provisioning:
Who may submit requests? The PRD leaves this open. Even without an approval step, Phase 1 needs authenticated, allowlisted submitters and clear permissions.
Which teams use services.insidemaps.com? The Ops team list must be explicit or derived from a controlled field.
What are the approved positions, account mappings, Google org units/groups, and licenses?
What is the approved behavior for non-Latin names, rehires, and suspended or previously deleted accounts?
What date, time, and timezone trigger offboarding? Confirm whether immediate termination is supported in this phase.
Can the InsideMaps system remove roles through a supported integration? If not, disclose and track that manual step; do not claim all access is blocked.
How are managers notified? The PRD calls for manager notifications but treats manager capture as later-phase work.
Is any approval required? The PRD places approvals later, but the business must explicitly confirm that authorized submission alone is sufficient for Phase 1.
MVP success measures
Capture the current baseline from the master sheet before launch, then measure:
Time from an authorized request to working accounts; target from the PRD: within 15 minutes once accepted for execution.
Time from leave effective time to access blocked; target: within 15 minutes.
Admin hands-on minutes per hire and leaver.
Share of requests completed without admin intervention.
Wrong account type, incorrect address, duplicate, and partial-provisioning incidents.
Share of requests with a complete audit trail and share of failures visible in the exception queue.
